# 0004. Auth на better-auth, данные изолированы по владельцу

Дата: 2026-10-22. Статус: принято.

## Контекст

Нужна базовая авторизация email+password с сессией, переживающей перезагрузку. Варианты: self-made JWT-модуль, готовый сервис, better-auth поверх собственной БД.

## Решение

better-auth (drizzle-adapter, PostgreSQL): таблицы `user/session/account/verification` живут в той же схеме Drizzle, миграции версионируются вместе с приложением. Сессия — httpOnly cookie; Fastify монтирует `/api/auth/*` без своих контент-парсеров, проксируя `Request` в `auth.handler()`.

Ключевая граница — `SessionResolver` (интерфейс): в проде — сессия better-auth, в моке — фиксированный демо-пользователь. Каждая процедура контракта авторизованная: middleware бросает типизированный `UNAUTHORIZED`, а репозиторий задач принимает `userId` явным аргументом — фильтрация «своих» данных невозможна на уровне запроса, а не по договорённости.

## Последствия

- Пароли не покидают сервер, XSS не читает сессию; CSRF-поверхность ограничена SameSite-куками.
- Тесты api ходят реальным HTTP (signUp + cookie-inject), не мокая auth.
- Цена: лишние таблицы и процесс в БД; смена провайдера auth — переписать `SessionResolver` и таблицы (не бесплатно, но локализовано).
